# Agent 作業規範（agent-ops）

本檔為生效的**作業治理**規範,源自 HS_AgentsLog pack,已對齊至 pack v0.7,並依本專案適配。
領域規則(文本模塊、結構、練習等)不歸本檔管,以 `Library/CURRENT.md` 指向的 canonical 分檔為準。

**術語分流**:本專案「模塊」一詞專指**文本模塊**(領域,見 `規範/10-模塊層.md`);
本檔治理的子系統稱**作業模塊**(作業模塊 ID)。兩者規則互不適用:文本模塊的自動切分、調整
不受本檔「作業模塊只能提案」限制;作業模塊登記表也不受領域規範的粒度細則約束。

作業模塊真相在本檔的登記表;看板(`docs/management/ops-board.md`)只追蹤檢查與變更,不定義作業模塊。
管線**站位**(F1、F2、F3a～F3d、T1～T3、R1、V1)與**成品代號**(C0、C1…)見 `docs/management/ops-id-legend.md`;站位與成品代號**不是**作業模塊,不得單獨登記、不得單獨記變更列主欄。舊站位代號 **F4** 已併入 **F3c**,不得再當現行站位主欄或摘要唯一代號(歷史變更列不回改)。

## 一、作業模塊登記表

作業模塊以**架構邊界／子系統**劃分(常一起改、一起驗的一塊),不以單一功能劃分。
功能與站位只用於摘要與路線標籤,不產生作業模塊 ID。初期維持 3～5 塊,被痛再拆。

| ID | 名稱 | 責任邊界(含哪些目錄/子系統) | 狀態 |
|---|---|---|---|
| M0 | 專案基盤 | CI、根目錄配置、README、`tools/` 雜項、**C0** 代號圖例與管線總覽等不屬於 F／T／R／V 的部分 | 生效 |
| M1 | 收錄與文本管線 | （舊）ingest-text、`Inbox/`、`DOC/` 收錄面 | 已廢止 |
| M2 | 結構與視圖 | （舊）extract-structure、render-knowledge-views、`tools/viz/`、React 儀表板 | 已廢止 |
| M3 | 練習與演講 | （舊）generate-practice、run-speaking-session | 已廢止 |
| M4 | 登記與驗證 | （舊）manage-skill-registry、validate-learning-pipeline | 已廢止 |
| F | 主管線 | 站位 F1、F2、**F3a～F3d**(平行可互調):文本收錄、模塊＋邊、策略 V2／最小一步、九宮、題目、演講;skills:`ingest-text`、`modularize-text`、`extract-structure`、`generate-practice`、`run-speaking-session`;`Inbox/`、`DOC/` 收錄面。**M5 不登記**(內容在 F3a) | 生效 |
| T | 轉換／視圖 | 站位 T1～T3:技能粗分用法、繪圖、HTML 輸出與 hub(成品 **C1-(T3)**);skills:`render-knowledge-views`;`tools/viz/`、HTML 管理中心 | 生效 |
| R | 正式對齊 | 站位 R1:`align(module)` 打勾／pending;skill:`manage-skill-registry`(與 T1 **共用同一技能登記簿**,不另開表) | 生效 |
| V | 驗證橫切 | 站位 V1:升格／開版抽查與管線驗證;skill:`validate-learning-pipeline`;可抽查 F／T／R 各站 | 生效 |

狀態值:`籌備`｜`生效`｜`已廢止`。M0 為常設作業模塊,不計入 3～5 塊上限,不得廢止。
**C0** 為 M0 名下的總覽／成品代號,不取代 M0。舊 M1～M4 編號不回收。

啟用流程(兩階段):

1. **規劃期——架構模塊化設計**:依藍圖劃出作業模塊,登記本表、狀態「籌備」。籌備中的作業模塊可被路線與規劃討論引用,但尚無檢查表,不得對其實作、不得在變更表記列。
2. **啟用**:使用者確認該作業模塊的必做檢查後,狀態改「生效」,同時在看板建立該節(必做 + 擴充檢查)。自此對該作業模塊的實作必須跑必做檢查並記變更列。可一次批量確認多個啟用。

籌備期試作:為驗證劃分,可進行試作(spike/原型)。試作不算正式實作,不受啟用限制;產出只記入試作紀錄(`docs/experiments/INDEX.md`),不得併入正式碼;試作結論用於支持提案與啟用。

啟用與升必做均須經使用者確認;Agent 只能提案。

登記規則:

- 表中作業模塊來源必須是藍圖的架構邊界;新作業模塊須先提案,使用者確認後才登記。
- 提案落點:寫入 `docs/management/decisions.md`,含建議的名稱、責任邊界與必做檢查。
- **作業模塊不自動變化**:Agent 只能提案,不得直接改表。(文本模塊不受此限,見術語分流。)
- ID 一經使用不得重用於不同意義;廢止的作業模塊標「已廢止」,不刪列。
- 廢止後:看板該節保留並標「已廢止」,不再跑其檢查;簡易變更表不得再以該 ID 記新列。
- 看板必須與本表同步:本表每個生效作業模塊,看板有且僅有一節。

## 二、檢查規則

- 每作業模塊必做檢查 2～3 條,上限 5 條;寫在看板該節內。
- 必做檢查條文視同本規範內容:只有使用者確認後才可增、刪、改;Agent 例行更新看板時只能勾稽結果,不得動條文。
- 完整檢查寫在該節「擴充檢查」小節,標明選讀,不得當預設全跑。
- 新增檢查預設進擴充;重複出事、確認夠硬後才**升必做**(須使用者確認)。
- 跨作業模塊工作:主模塊跑全部必做;波及模塊最多加跑一條關聯檢查,不整段複製。

語意分界:必做是義務——不跑不得標完成,因此刻意壓少;擴充是選項庫——預設不跑,
只在大改、發版或使用者要求時跑。判準:「這條不跑,敢不敢標完成?」敢=擴充,不敢=必做。

自動收檢與計數(Agent 在擴充檢查內的唯二自動權限:新增條文、計數 +1):

- **Bug 收檢**:`bug` 列標「完成」前,必須同時在該作業模塊擴充檢查加一條回歸檢查,
  格式 `回歸:<一句話> ← #<變更列編號> ×1`;未加不得標完成。
- **功能收檢**:`新增` 列標「完成」時,加一條驗證檢查,格式 `驗證:<一句話> ← #<變更列編號>`(不計數)。
- **計數**:只有「該條檢查實際攔到失敗」或「同型 bug 再次發生」才 +1,並在條尾追記變更列編號;
  跑過但未攔到不計。Agent 只能 +1,不得歸零、不得刪條。
- **提案線(×2)**:回歸檢查計到 ×2,Agent 必須提案升必做,附證據(各次的變更列編號);升格仍須使用者確認。
- **出清**:單一作業模塊擴充檢查超過 10 條時,Agent 提案合併同類、淘汰長期 ×0 或未再攔到的舊條;
  合併與淘汰均須使用者確認。自動進、手動出。

## 三、變更記錄規則(簡易變更表)

所有新增、修 bug、重構、文件工作,各在看板檔末簡易變更表記一列:

```
# | 日期 | 類型 | 作業模塊 | 摘要 | 檢查 | 狀態
```

- 類型:`新增`｜`bug`｜`重構`｜`文件`
- 狀態:`進行中`｜`完成`｜`阻塞`｜`已歸檔`
- 作業模塊欄必須是登記表中狀態「生效」的 ID(現行:`M0`／`F`／`T`／`R`／`V`);一列一件事,摘要一句話。
- 站位(F1、F2、F3a～F3d、T1～T3、R1、V1)與成品代號(C0、C1…)只寫在摘要(如「F／F3a」「C1-(T3)」),不得當作業模塊欄的值。
- 管理與規劃類工作(藍圖、規範、看板、交接、提案等管理文件)欄位填「—」,不受啟用限制。
- 跨作業模塊工作:只記主模塊,波及模塊在摘要內附註(如「波及 T」),不另開列。
- 檢查欄記錄必做檢查結果(通過/未跑/失敗原因),不得留白即標完成。
- 完整時間與細節寫進交接快照,不寫進此表。

壓縮:表超過 25 列、或已完成列明顯佔多數時,整表凍結存入
`.agents/handover/reference/change-log/YYYY-MM-DD.md`,看板保留:一列歸檔指標 + 全部未結案列 + 必要近期列。

## 四、修 bug 流程

1. 判定所屬作業模塊 ID,且狀態須為「生效」;判不出、不存在或僅「籌備」→ 停止並回報,提案寫入 `docs/management/decisions.md`。
2. 簡易變更表先記一列:`bug / 進行中`。
3. 只在該作業模塊責任邊界內修改;需跨界時回報,不擅自擴大範圍。
4. 修畢跑該作業模塊必做檢查;失敗則狀態保持進行中並記原因。
5. 通過後標 `完成`,並依第二節「Bug 收檢」在該作業模塊擴充檢查加回歸檢查;未完成必須留表,且進交接快照的未解事項。

## 五、交接快照規則

- 快照檔名:`.agents/handover/YYYY-MM-DD-NN.md`(NN 為當日序號,01 起)。2026-07-18 前的 commit-ID 命名快照為歷史,不改不刪。
- 快照必含五欄:完成範圍、檢查結果、未解事項、下一步、完整變更時間表(含細節時間,簡易變更表不記的都記這裡)。
- 快照建立後不可變;後續修正另建新快照,不改舊檔。
- `docs/management/current-handover.md` 只放指向最新快照的連結與一句話狀態,不承載交接正文。
- 交接時附上簡易變更表本次區間與全部未結案列。

## 六、規範修改程序(更新卡)

- 修改本規範、`AGENTS.md` 的規則內容或必做檢查條文前,Agent 先在對話輸出**更新卡**,使用者確認後才落檔;未經更新卡確認的規則修改無效,發現時回報並回退。
- 更新卡固定四格:改了什麼(白話,以前→現在);使用者要做的事;使用者不用記的事;落點(將修改的文件)。
- 確認後落檔,並在「更新史」(`CHANGELOG.md`)追加一條:版本、日期、三行以內白話。更新史只追加、不回改。
- 更新幅度大時(新增機制、改變工作流程),完整更新卡另存 `.agents/handover/reference/update-cards/YYYY-MM-DD.md`;小修小補只記更新史一條,不留卡。
- 領域規範(CURRENT 分檔)的修改不走本節,依其原有版本與裁決機制(`規範/70-版本與裁決.md`)。

## 七、Agent 行為底線

- 缺作業模塊 ID → 停止實作並回報,不得自創;不得把站位或成品代號當作業模塊 ID。
- 只改本次範圍;不順手重構未涉及的作業模塊。
- 不在 `DOC/`、`Inbox/` 建立任何規範、看板或帳本。
- 本檔與看板衝突時以本檔為準,並回報衝突,不擅自改對齊。
- 本檔與領域規範各管各的:工作方式聽本檔,產物規則聽 CURRENT;真發生交集衝突時停止並回報,不擅自裁決。
- 回覆與產出須遵守「記憶」現行條目;與記憶衝突的內容不得輸出。
- **流程／結構圖同步**:當作業流程規則(本檔／`AGENTS.md` 流程相關條文)或管線結構真相(`ops-id-legend` 代號／站位／成品範圍、本檔登記表邊界)變更且影響已掛名的流程圖時,同次工作必須:(1)更新對應來源 `*.workflow.json`(不得只手改 HTML);(2)重渲染 HTML;(3)若該圖已封存或不再維護,改標封存／改掛後繼並自 hub 主入口移除。HTML 流程圖為投影,與真相衝突時以文檔為準、圖視為過期。詞彙「流程圖」見 `docs/management/flow-map.*`。

## 八、記憶規則

「記憶」（`docs/management/memory.md`）為跨 session 的禁項／邊界帳本,與「偏好」分開。

### 必讀

- 「接手」時必讀記憶;目標專案缺檔時回報缺失,不得當選配跳過。
- 實作與回覆期間,已讀過的現行條目持續有效,不需每輪重讀,除非使用者改過記憶或明確要求重讀。

### 詢問列入

- 當使用者在**回覆中**以短句提及「不要／禁止／別再…」等邊界（且內容屬其本人意旨,非長文章、非外部來源貼文全文）時,Agent 須詢問是否列入記憶。
- 問法簡潔,例如:「要不要把『……』列入記憶？」使用者確認後才寫入;否認或忽略則不寫。
- 不得把長文、論文、網頁全文、大段引用自動拆進記憶;這類材料最多摘要後再問是否記**一句禁項／結論**。
- Agent 不得擅自新增、刪改記憶條目。

### 與偏好

- 「偏好」管怎麼協作;「記憶」管不要什麼。衝突時以記憶禁項為準。
