## 0. 目的

把目前三條已存在、但用途不同的流程串成一個可實際使用的整體：

1. **WORK**：真實任務／專案的外顯執行流程。
2. **LEARN**：REBUILD1 現行學習流程，處理「不會做／看不懂／能力缺口」。
3. **VERIFY**：D32～D34 的內容製作與分級驗證，處理「這個結果／主張能下多強的結論」。

整合目標不是把三套規則壓成同一套，而是建立清楚的**切換條件與返回點**。

---

## 1. 核心結論

三條流程可視為同一個抽象循環的不同外顯：

```text
目標
→ 找已有資源
→ 調用／組合
→ 執行
→ 發現卡點或不確定
→ 補缺／替換／調整
→ 驗證
→ 沉澱
```

本稿暫稱這個抽象循環為 **OSA Core**。

**OSA Core 只是一個對齊模型，不新增 L 層、不新增作業模塊、不取代任何既有規範。**

---

## 2. 三種模式的責任邊界

| 模式 | 核心對象 | 主要問題 | 主要輸出 |
|---|---|---|---|
| **WORK** | 真實任務／專案 | 怎麼把事情做成？ | 可驗收成果、SOP、能力／工具組合 |
| **LEARN** | 學習者的能力缺口 | 哪裡不會，怎麼補到能繼續？ | 局部學習路徑、可返回原流程的能力 |
| **VERIFY** | 主張／方案／發布內容 | 現有證據允許下多強的判斷？ | 驗證結果、判斷、驗證物／內容 |

治理層 **V1** 不屬於上述三種模式；它仍是管線橫切抽查。

---

## 3. WORK｜外顯做事流程

WORK 是最外層主循環：

```text
需求／目標
→ 找現成能力
→ 調用與組合
→ 執行
→ 排錯
→ 替換／調整
→ 驗證結果
→ 沉澱可複用流程
```

### 3.1 原則

- 能調用就不重造。
- 能組合就不從零開發。
- 優先處理整合、排錯與關鍵缺口。
- 只有現成能力確實不能滿足核心需求時，才新增能力／自行造輪子。

### 3.2 「找現成能力」的範圍

能力可以是：

- AI／Agent／模型能力。
- Skill／工具／API／library。
- 現有程式、模板、SOP。
- 人的既有能力。
- LEARN 中已存在的知識結構與局部路徑。

WORK 不要求所有能力都先被學會；只要求能被可靠調用、組合與驗收。

---

## 4. LEARN｜REBUILD1 學習支線

LEARN 直接沿用 `REBUILD1-framework.md`，不重定義其 L0～L3。

WORK 發生以下情況時，可進入 LEARN：

- 不知道下一步怎麼做。
- 看不懂必要材料。
- 無法判斷某個策略卡點。
- 現成工具存在，但缺少操作／判斷能力。
- 排錯後確認問題不是工具本身，而是人的前置能力不足。

局部切換：

```text
WORK 卡點
→ LEARN:L1-02 定位卡點
→ LEARN:L3-01 查／調 L2 資源
→ LEARN:L3-02 組最小材料
→ LEARN:L1-04 局部路徑
→ 通過
→ LEARN:L1-05 返回
→ 回到原 WORK 節點
```

若 L2 缺資源，仍依 REBUILD1 規則觸發相應 SK 備料；不因 WORK 接入而改寫 LEARN 的既有協議。

**LEARN 的完成不是「學完整個領域」，而是補到足以返回 WORK。**

---

## 5. VERIFY｜內容／證據驗證支線

VERIFY 沿用 D32～D34，不改變既有「驗證項目、開發日誌、L1／L2／L3 驗證等級」定義。

為避免和 REBUILD1 的 L1／L2／L3 功能層混淆，本整合稿跨系統敘述時使用系統前綴：

- `VERIFY:L1`＝D32 的 L1 探路。
- `VERIFY:L2`＝D32 的 L2 決策驗證。
- `VERIFY:L3`＝D32 的 L3 研究驗證。
- `LEARN:L1`／`LEARN:L2`／`LEARN:L3`＝REBUILD1 功能層。

這只是跨系統引用格式，不改 D32／D33 的正式名詞。

### 5.1 何時從 WORK 進 VERIFY

不是每個 WORK 都必須進 VERIFY。只有需要形成正式判斷時才進，例如：

- 要判斷某方向值不值得繼續投入。
- 要判斷某方案在特定情境是否值得採用。
- 要發布帶有可核對結論的內容。
- 要提出研究級主張或重大實務方向。

基本切換：

```text
WORK 產生結果／候選方案
→ 判斷是否需要正式結論
   ├─ 否：留在 WORK，以任務驗收結案
   └─ 是：建立 VERIFY 驗證項目
          → 選 VERIFY:L1／L2／L3
          → 執行驗證
          → 形成相應權限的判斷
          → 返回 WORK 決策／沉澱／發布
```

---

## 6. 三種「驗證」禁止混用

| 名稱 | 問題 | 所屬 |
|---|---|---|
| **WORK 任務驗收** | 成果有沒有符合原需求／完成條件？ | WORK |
| **VERIFY 內容驗證** | 證據允許下多強的結論？ | D32～D34 |
| **V1 管線抽查** | 系統流程／規範有沒有漏步驟或違規？ | 作業治理 |

三者可以針對同一項工作發生，但不是同一個 Gate。

---

## 7. 完整串接

### 7.1 正常路徑

```text
WORK
需求／目標
→ 找現成能力
→ 調用／組合
→ 執行
→ 任務驗收
→ 沉澱
```

### 7.2 能力不足

```text
WORK 執行／排錯
→ 確認是人的能力缺口
→ LEARN 局部補能力
→ 返回原 WORK 節點
→ 繼續執行
```

### 7.3 需要正式判斷

```text
WORK 取得候選結果
→ VERIFY 建立驗證項目
→ 依結論權限跑 VERIFY:L1／L2／L3
→ 返回 WORK
→ 採用／調整／停止／發布／沉澱
```

### 7.4 同時缺能力又缺證據

預設先處理「能不能做」，再處理「能不能下結論」：

```text
WORK
→ LEARN 補足必要能力
→ 回 WORK 產生可觀察結果
→ VERIFY 檢查證據與結論權限
→ 回 WORK 作最終處置
```

若 VERIFY 執行過程本身發生能力缺口，也可以局部呼叫 LEARN；完成後必須返回原 VERIFY 驗證項目，不另起一條平行主線。

---

## 8. 沉澱分流

完成一輪後，不把所有產物塞回同一個庫：

| 產物 | 去向 |
|---|---|
| 已驗收的執行方法、工具組合 | WORK：SOP／能力組合／可複用工作流 |
| 可支援後續卡點的知識結構 | LEARN：依 REBUILD1 的 L2／相關資源規則處理 |
| 正式驗證問題、證據、判斷 | VERIFY：驗證項目／驗證物／發布內容 |
| 管線規則與檢查結果 | 治理：R／V／既有管理入口 |

原則：**沉澱的是未來會被重新調用的東西，不要求保存所有學習與執行細節。**

---

## 9. 切換判斷表

| 當下問題 | 去哪裡 |
|---|---|
| 「我要把這件事做完」 | WORK |
| 「我不知道這一步怎麼做」 | LEARN |
| 「工具壞了／組合不起來」 | 先留 WORK 排錯；確認是能力缺口才進 LEARN |
| 「這個結果算不算支持我的說法」 | VERIFY |
| 「這方案值得採用嗎」 | VERIFY:L2 或依 D32 強制條件升級 |
| 「這方向值得再投入一輪嗎」 | VERIFY:L1 |
| 「流程本身有沒有違反規範」 | V1／治理 |

## 10. 與既有框架的關係

### 10.1 REBUILD1

- 保留為**現行學習框架**。
- 本稿只定義 WORK 如何呼叫／返回 LEARN。
- 不把 WORK 節點硬塞成新的 L0～L3。
- 不把 OSA Core 升成 L4 或新的 Skill。

### 10.2 D32～D34

- 保留為**內容製作／驗證規範**。
- 本稿只補上 WORK 何時需要 VERIFY、驗證後返回哪裡。
- 跨系統引用時加 `VERIFY:` 前綴以避免和 REBUILD1 L 層撞名。
- 不把 WORK 任務驗收冒充為 D32 驗證完成。

### 10.3 作業治理

- F／T／R／V 不因本稿重編。
- V1 仍是橫切抽查，不變成 WORK 或 VERIFY 的必經主節點。

## 11. 最小實作建議

本稿若進入試行，不先做大改版；只需要驗證三件事：

1. 任取一個真實小專案，能否以 WORK 從需求跑到任務驗收。
2. 人為選一個真實能力卡點，能否切入 REBUILD1 LEARN，補完後精確返回原 WORK 節點。
3. 對該專案的一個候選結論建立 VERIFY 驗證項目，完成後能否返回 WORK 作處置，且不混淆任務驗收／內容驗證／V1。

三項跑通後，再決定是否：

- 把 WORK 寫成正式規範。
- 在 RBF1 增加「外部呼叫／返回」說明。
- 在 D34 增加 WORK 作為上游／下游的銜接縫。

## 12. 本稿不做

- 不升格 canonical。
- 不修改 D32／D33 的正式驗證名詞。
- 不改 REBUILD1 的 L0～L3 主鍵。
- 不新建 OSA Core 作業模塊。
- 不要求所有 WORK 都建立驗證項目。
- 不要求所有工具使用都先進 LEARN。
- 不把「做成」等同「證據足夠」。

---

## 13. 一句話架構

> **WORK 負責把事做成；LEARN 在能力不足時局部補足並返回；VERIFY 在需要正式判斷時限制證據與結論權限；三者共享 OSA Core 的抽象循環，但各自保留自己的真值與狀態。**
