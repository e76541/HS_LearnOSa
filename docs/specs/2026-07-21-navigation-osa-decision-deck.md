## 1. 目的轉向

舊主流程：

```text
文本 → 模塊／邊 → 練習 → 熟練 → 演說
```

新主流程：

```text
真實目的
→ 定位當前情境
→ 找出會改變路線的必要判斷
→ 使用者能判斷：直接選擇
→ 使用者不能判斷：診斷缺口 → 補最小知識 → 重新判斷
→ 選擇改變後續牌組
→ 執行下一步並回報結果
→ 重新定位／導航
```

終點不是「完成課程」，而是**使用者在真實任務中能作出有依據的選擇，並獲得可執行的下一步**。學習不消失，但由主目的改為導航中的按需能力形成。

### 1.1 終極主張（待裁決）

> OSA 能從可追溯的課程知識中，為當前目的組合最小決策路徑；在使用者無法判斷時提供必要而不過量的學習，讓使用者自己選擇並推進任務。

### 1.2 刻意不做

- 不要求先學完課程才開始任務。
- 不把固定課程順序改名為牌組。
- 不由 Agent 默默替使用者作高影響決定。
- 不把一次情境生成的路徑回寫成通用知識真值。
- 不在本階段把 Resource2Skill 類可執行技能當成前置條件。

## 2. 三層模型

```text
證據層                  決策投影層                 導航控制層
原文／組件／模塊／邊  →  前置閘門＋引導＋方案比較  →  目的牌組＋目前位置＋分支
```

| 層 | 主要物件 | 責任 | 是否真值 |
|---|---|---|---|
| 證據層 | Source、Fragment、Module、ModuleEdge、SkillNode | 保存課程主張、方法、條件、案例與關係 | 是；沿現行可追溯規則 |
| 決策投影層 | DecisionCard、DecisionReadiness、Guide、OptionProfile、Impact、EvidenceRef；（訓練擴充）TextCard、NodeCard、MechanismCard、BlindSpotCard | 先確認能否決定，再把知識轉為「要考慮什麼、有哪些方案、選了會怎樣」；訓練模式另做文本分流與機制對照 | 可重建投影，不取代模塊 |
| 導航控制層 | GoalSession、Deck、RouteState、DecisionRecord、DecisionReview | 依目的、情境、選擇與實際結果動態組牌、重排下一步 | 場次狀態，不回灌證據層 |

核心邊界：**模塊不改成牌。模塊是牌的證據；決策牌是導航介面；牌組是情境生成的路徑。**

**旅程式導航（2026-07-24 抽出）**：導航控制層可包裝為 **Journey**（終點＝文本或專案）→ 有序 **GATE**（預設站＋過站條件）→ 站內仍走決策牌循環；**STEP**＝最小可執行動作計數。證據層（模塊／邊）不動。細節見 [F3a 導航模式抽出](2026-07-24-f3a-navigation-mode-extract.md)。

## 3. 決策前置閘門與決策牌

一張牌只承載一個足以改變路徑的判斷。純知識摘要、無後續影響的問題、可由系統確定性推導且無需使用者裁量者，不獨立成牌。

### 3.1 決策前置閘門

正式比較方案前，先判斷「現在是否已具備作決定的條件」。頂層欄位固定，欄內細項依領域、文本與當前情境生成：

```yaml
DecisionReadiness:
  decision_ready: true | false | forced
  authority: 誰有權決定，以及權限邊界
  information_sources: 現有資訊、來源與可信度
  source_conflicts: 來源間的矛盾
  unknowns: 可能改變答案的未知項
  deadline: 最晚決定時間與逾時代價
  can_wait: 能否等待補充資訊，以及等待成本
```

固定的是頂層介面，不是萬用細項。例如 `authority` 在歷史案例可展開為正式授權、政治正當性與軍事控制；在網站專案可展開為決策負責人、客戶限制與團隊核准。原文沒有提供的內容標示「作者未提供」或「未知」，不得為填滿模板而補造。

前置閘門只有三種出口：

```text
資訊與權限足夠 → 進入考量展開與方案比較
資訊不足但可等待 → 先查證，暫不作決定
資訊不足且不能等待 → 強制風險決策，明示假設、監測訊號與退路
```

前置閘門的作用不是替使用者選，而是避免系統回答一個尚不能可靠回答的問題。

### 3.2 引導與方案分工

同一張決策牌內分成兩種可重用投影：

| 投影 | 回答的問題 | 不負責 |
|---|---|---|
| `Guide` | 這類決策可能漏想哪些考量？ | 不先推薦特定方案 |
| `OptionProfile` | 各方案在已確認考量上表現如何？ | 不決定使用者在乎什麼 |

```yaml
Guide:
  guide_id
  decision_type
  concerns:
    - concern_id
      prompt
      why_it_matters
      evidence_refs

OptionProfile:
  option_id
  context
  concern_impacts:
    - concern_id
      gain
      cost
      risk
      failure_signals
  reversibility
  fallback
  valid_time
  evidence_refs
```

新增方案時只補 `OptionProfile`；發現新盲點時只補 `Guide`，再逐步補各方案對該考量的資料。一次情境生成的考量清單仍是投影，不回寫成證據真值。

### 3.3 決策牌最小欄位

```yaml
DecisionCard:
  card_id
  decision: 現在要決定什麼
  why_now: 為何此刻必須決定
  trigger_conditions: 何時需要這張牌
  readiness: 決策前置閘門
  guide_refs: 本次用來展開盲點的引導投影
  selected_concerns: 使用者確認本次重要的考量
  options:
    - option_id
      label
      fit_conditions
      impacts:
        - concern_id
          direction
          explanation
      risks
      reversibility
      next_cards
  assumptions: 資訊不足但不能等待時採用的假設
  evidence_refs: 支撐條件與影響的模塊／字元區間
  diagnostic_prompts: 判斷使用者是否具備選擇能力
  minimal_learning_refs: 不會時才展開的最小知識
  completion_rule: 何時視為已作出有效選擇；只得在全域最低作答形制（§5：選項＋理由＋成立條件）之上加嚴，不得降低（2026-07-23 縫 B 裁決）
```

### 3.4 牌面與翻牌

正面只顯示：

1. 要決定什麼。
2. 為什麼現在要決定。
3. 尚缺哪些事實，以及現在能否決定。
4. 可能漏想的考量點。
5. 經使用者確認後，才顯示選項與最重要影響。

翻牌才顯示：

- 適用條件、風險、可逆性與完整影響。
- 課程依據及原文回指。
- 「我不知道怎麼選」的診斷入口。

系統可提出建議，但必須同時顯示理由、假設與受影響路徑；高影響或不可逆選擇不得替使用者完成。

### 3.5 動態考量與通用提示

不把所有決策硬套同一組維度。MVP 先以六個通用提示協助展開考量，再依領域、文本與情境增減；它們不是封閉 schema，也不要求每張牌全部使用：

| 通用提示 | 例子 |
|---|---|
| 時間 | 上線速度、學習時間、維護時間 |
| 成本 | 初始成本、持續費用、轉換成本 |
| 複雜度 | 要新增的元件、協作與維護負擔 |
| 能力／彈性 | 現在能做什麼、未來可擴張到哪 |
| 風險 | 安全、可靠性、法務、供應商鎖定 |
| 可逆性 | 選錯後能否回頭、回頭代價多高 |

考量點由 Guide 提出，使用者確認本次真正重要者後才進方案比較。影響不得只有「高／中／低」而無說明；每項影響至少要能回到模塊主張、方法條件或案例證據。

### 3.6 決策結果與回顧

系統不只保存「選了什麼」，還要保存當時狀態、理由、放棄項、預期與重新評估條件：

```yaml
DecisionRecord:
  decision
  state_snapshot
  choice
  choice_reason
  accepted_costs
  rejected_options
  assumptions
  expected_outcome
  reassessment_triggers

DecisionReview:
  actual_outcome
  expectation_gap        # expected_outcome vs actual_outcome 的落差；keep_or_switch 的唯一依據
  missed_concerns
  keep_or_switch         # 依 expectation_gap＋reassessment_triggers 判定，不憑事後歸因
  guide_update_candidate
  node_card_ref          # 選配：升級口——需要歸因時升級為 NodeCard，互指不複製
```

**刪欄（2026-07-23 縫 A 裁決）**：原 `what_worked`／`what_failed` 為自由歸因欄，無對照層四判定保險絲，易憑結局後見之明歸因，違反「不因結局追認決策品質」——刪除。Review 只管「預期 vs 實際落差」與重評觸發；需要歸因時走**升級口**：`DecisionRecord` 升級為 `NodeCard`（補機制假設與 A 資訊集），由訓練對照層四判定管歸因（見 [決策訓練器 v2 §3.1](2026-07-23-decision-trainer-v2.md)）；兩卡互指引用、不複製欄位。

回顧產生的是候選改進：可提高某考量的提示優先級，或補方案證據；未經覆核不得直接改寫通用 Guide 或證據層。

### 3.7 活棋、文本邊界、跨源與霧戰（2026-07-22 討論補）

決策牌要有效，靠的是**互斥活棋與狀態改寫**，不是編平行宇宙，也不是純史實重播。

**活棋原則**

- 選項只許來自：原文出現過的行動、建議、兩說、壓力或可選路徑。
- 禁止為「多線好玩」編寫原文未支撐的完整平行結局。
- 純史實重播（選項皆裝飾、牌組不增刪）不足以驗收牌組效用。

**文本邊界結束**

- 使用者選了原文未續寫的線：標「原文未展開此線」，停在已寫風險／監測訊號／換源，不得續造後續劇情。
- 可執行下一步改為查證、等待或帶明示假設的強制決策，不假裝課文有結局。

**單篇沉默 ≠ 全域無路**

- 文本 A 沒提某路線：不得掛 A 的 `char_span` 偽造該 option。
- 文本 B 的模塊可支撐相關 option／影響：`evidence_refs` 必須指向 B；不得回寫進 A 的模塊本體。
- GoalSession 宣告資訊集：`single_source`（嚴格只活在一篇）或 `multi_source`（課群導航）。多源衝突寫入 `source_conflicts`，不合併成一句真值。

**主角／霧戰（選配）**

- 牌正面預設只給「決策當下可知」；後文結局僅結算回放或翻牌揭示，不得作代選依據。
- 沉浸靠資訊集與閘門，不靠編內心戲；原文沒寫的動機標未知。
- **資訊集雙判準（2026-07-23 縫 D 回寫）**：語義判準＝已知／不可知可乾淨切割（B2，整理稿 §1）；機械判準＝模塊化來源以 `a_cutpoint`（char_span 切點）判定牌面可見範圍，切點前模塊＝已知集（訓練器 §5.5），不靠人工列舉。兩判準同指一件事，機械判準是語義判準的落地，不是第二套標準。

管線掛點見 [管線整合（脊柱至 F3 前）](2026-07-22-pipeline-deck-nine-grid-integration.md)。

### 3.8 訓練模式卡牌（決策訓練器 v2）

導航模式之外，另開**訓練／對照模式**（細節見 [決策訓練器 v2](2026-07-23-decision-trainer-v2.md)）：

| 卡 | 職責 | 與本節既有物件 |
|---|---|---|
| `TextCard` | intake 打 A–E 類型＋三要素勾稽 | 在證據層之前分流；E 類可直入機制庫 |
| `NodeCard` | A 資訊集／凍結作答／B 或佔位／對照判定 | 擴充 `DecisionRecord`；`DecisionReview` 需歸因時經升級口指向之（§3.6）；可與 `DecisionCard` 互指，不合併真值 |
| `MechanismCard` | 可檢驗機制＋失效條件；跨案例引用 | 參考類別正式化；不升格為模塊 |
| `BlindSpotCard` | 對照層一句話盲區序列 | 個人弱點軌跡，不回灌證據層 |

協議共用：作答＝選擇＋可檢驗機制假設；對照驗證機制不驗證選擇對錯；風險以 A 時刻資訊集評估。不符合 A–E 不強行套類，走開放擴充（見該草案 §6）。

**導航入口門檻（2026-07-23 縫 C 明文）**：文本進導航模式的門檻＝具**活棋**（§3.7：選項來自原文支撐）＋通過**決策前置閘門**（§3.3）；TextCard A–E 分流只管訓練／對照入口，**不是**導航入口條件（分流亦非必經閘，見訓練器 §5.1）。

**雙模式正式接受（2026-07-23 裁決，原整理稿待裁 4）**：導航／訓練兩模式為 F3a 正式結構，非暫行並存。共用**作答形制**——選擇＋可檢驗的理由／條件（導航「選項＋理由＋成立條件」＝訓練「如果 X，因為 M，導致 Y」的同族弱化形；全域最低門檻見 §5）。**四判定為訓練模式專屬**：對照層需要 B 路徑與對照組，導航沒有；導航需要歸因時走升級口（§3.6→NodeCard），不在導航內建輕量四判定。

## 4. 動態牌組

牌組不是預製課綱，而是某次 `GoalSession` 的最小決策子圖。

```text
目的＋已知情境
→ 找候選決策牌
→ 跑前置閘門：權限、資訊衝突、未知、期限
→ 展開可能漏掉的考量，由使用者確認本次重點
→ 移除當前不相關／未觸發的牌
→ 依前置事實與路徑影響排序
→ 只顯示目前牌＋近端預覽
→ 使用者選擇
→ 加入、移除或改排後續牌
```

### 4.1 最小路徑定義

> 在目前已知條件下，不遺漏必要判斷，且不加入尚未觸發之支線的最短可執行路徑。

最小不等於一次算死。每次取得新事實、完成一步或遭遇失敗，都允許重新組牌。

### 4.2 牌組顯示

- 預設顯示「目前牌」及後續一至三張的模糊預覽，避免使用者被整棵決策樹淹沒。
- 可展開全圖查看分支，但未觸發支線標為「可能」，不得偽裝成必做。
- 已排除的牌保留排除理由，方便回溯路徑為何縮短。

## 5. GRILLME／前沿輪的位置

GRILLME 不再遍歷整門課，而是在**使用者無法完成某張決策牌**時，診斷該決策需要的最小知識前沿。

```text
決策牌：是否需要資料庫
→ 使用者無法說明要保存哪些資料
→ 前沿輪檢查：持久化／共享／查詢／更新
→ 找到第一個未知前沿
→ 只補對應模塊
→ 回到同一張決策牌重新選擇並說明理由
```

規則：

- 題目與講解仍須有課程證據，不憑空補答案。
- 診斷前不先給建議答案。
- 補知後必須回到原決策，不以「看過內容」視為完成。
- 有效完成至少包含：選項、理由、成立條件；必要時附不確定項。此即**全域最低作答形制**（2026-07-23 裁決）：各牌 `completion_rule` 只能在此之上加嚴、不得降低；與訓練模式「選擇＋可檢驗機制假設」同族（見 §3.8），全域共用「不因結局追認決策品質」。
- 熟練度可作解釋深度的參考，但不得自動替使用者選牌。

## 6. 網頁目的示例

輸入：`我要做一個展示作品、讓客戶聯絡我的網頁。`

定位後的首批牌：

| 決策牌 | 可能選擇 | 對路徑的影響 |
|---|---|---|
| 主要訪客要完成什麼行動？ | 看作品／聯絡／購買 | 決定頁面與轉換流程 |
| 內容由誰更新、多久更新？ | 開發者偶爾改／非工程人員常改 | 決定靜態內容或 CMS 支線 |
| 是否需要保存使用者或業務資料？ | 不需要／只收表單／需要持續查詢 | 決定資料庫、API、權限支線 |
| 是否有登入或付款？ | 無／登入／付款 | 決定身份、安全、金流與法務支線 |
| 誰負責長期維護？ | 自己／客戶／外包 | 影響技術選擇與交付形式 |

若使用者選擇「固定作品＋第三方聯絡表單＋無登入付款」，系統移除資料庫、身份與金流支線，得到：

```text
定義主要行動
→ 整理內容結構
→ 選靜態網站方案
→ 製作頁面與聯絡入口
→ 行動版／可用性檢查
→ 部署
```

若使用者不知道「是否需要資料庫」，才翻牌學習持久化與資料責任；理解後由使用者說明自己的資料需求，再決定是否加入後端支線。

## 8. MVP

### 8.1 範圍

- 一個真實目的領域，建議使用「完成並上線一個簡單網站」。
- 三至五份已有課程／文件來源。
- 五至十張人工整理的決策牌。
- 三個不同情境：純展示、內容管理、需要資料保存。
- 先人工組牌與重新導航，不做自動抽牌模型。

### 8.2 一次輸出

```text
目的
目前已知條件
決策是否就緒；若否，應查證、等待或帶假設決定
仍缺的必要事實
目前決策牌
可能漏想的考量點
使用者確認的重要考量
選項及最重要影響
建議與假設（可有，但不代選）
不會時的最小學習入口
選擇後的下一步與支線變化
課程證據
```

### 8.3 驗收

| 指標 | MVP 判準 |
|---|---|
| 路徑相關性 | 未加入與當前情境無關的主要支線 |
| 必要判斷召回 | 人工基準認定的高影響判斷沒有漏掉 |
| 影響可解釋 | 每個主要影響都有條件、理由與證據 |
| 決策就緒 | 資訊或權限不足時不直接推薦；能進入查證或強制風險決策 |
| 盲點展開 | Guide 至少能提出人工基準中的高影響考量，且不強迫套用無關維度 |
| 最小補知 | 使用者不會時只展開完成當前決策所需內容 |
| 使用者決策權 | 系統沒有把高影響／不可逆選擇當成確定答案代選 |
| 可重導航 | 新事實或失敗發生後，牌組能合理增刪與改排 |
| 任務推進 | 使用者得到可立即執行的下一步 |

學習輔助訊號另記：使用者是否能用自己的情境說明選擇、條件與取捨。此訊號不得取代任務推進指標。

## 9. 分階段規劃

| 階段 | 目的 | 產物 | 進入下一階段條件 |
|---|---|---|---|
| P0 目的裁決 | 確認產品轉向與三層模型 | 本稿裁決；舊草案沿用矩陣 | 使用者確認終極主張與邊界 |
| P1 紙上試跑 | 驗證決策牌是否真能縮短路徑 | 1 個目的、3 情境、5～10 張牌、至少 1 個「尚不能決定」案例、試作記錄 | 高影響判斷無明顯漏失；前置閘門可阻止過早推薦；牌組能隨選擇改變 |
| P2 Schema 試作 | 驗證欄位與證據回指 | DecisionReadiness／Guide／OptionProfile／DecisionCard／GoalSession JSON 草模與檢查器 | 固定頂層可機械檢查；動態細項、影響、條件、來源及分支可追溯 |
| P3 導航 Runtime | 讓使用者逐牌決策並重導航 | 最小 CLI／UI；場次狀態 | 三種情境走通；錯誤選擇可回退或改路 |
| P4 按需補知 | 接入 GRILLME 與最小學習 | 決策點診斷、模塊提取、回問 | 補知後能回到同牌作出有效決策 |
| P5 選配執行 | 評估是否調用可執行 Skill | Resource2Skill 類資產的有限接點 | 另行裁決；不改變使用者決策權 |

P1 前不得直接進 P2～P5；此處的試作不併入正式碼。
