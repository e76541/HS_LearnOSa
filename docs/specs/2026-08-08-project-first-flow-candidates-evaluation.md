- 狀態：草稿
- 裁決來源：無
- 實作參照：無
- 後繼：先完成 B0 現行 baseline 的同題試跑，再依相同案例逐一評價 B1～B5；本稿不直接改 RBF1／D48／D37／D38／canonical

- 日期：2026-08-08

- 現行主幹參照：D48、D49、RBF1、D37、D38
- 驗證／紀錄參照：D32～D34

## 0. 目的

把本輪對話中出現過的流程版本全部保留為**備選方案**，不再用後一版覆蓋前一版，也不因敘事較簡單就直接宣稱「更好」。

固定順序：

1. **先處理舊版／現行 baseline。**
2. 再按出現順序評價新候選。
3. 所有版本使用同一組評判標準。
4. 沒有通過概念自檢與同題試跑者，只能稱「候選」，不得稱「優化完成」。

本稿為比較草案，不代表使用者已採納任何候選。

## 1. 評判標準

### 1.1 十二項標準

| # | 指標 | 要問的問題 | 合格條件 |
|---|---|---|---|
| E1 | 單一責任 | 同一決策是否有兩套系統都能做？ | 每個核心決策只有一個 owner |
| E2 | 單一真值 | 同一狀態是否有兩份可能互相矛盾的真值？ | 每項核心狀態只有一個 source of truth |
| E3 | 必要步驟 | 是否增加非必要前置、Gate 或轉換？ | 不增加；或增加步驟有可核對收益 |
| E4 | 分支複雜度 | 執行時需要多少次分類／路由？ | 不增加；或一個新分支能取代更多舊分支 |
| E5 | 重複處理 | 同一文本／知識／路徑是否被重拆、重算、重建？ | 不重複；或重複有明確 cache／reuse |
| E6 | 回寫衝突 | 一個系統改狀態會不會破壞另一系統依賴？ | 唯一寫入權；或明確不可回寫 |
| E7 | 可追溯性 | 最終能否追回輸入→路徑→事件→輸出？ | 一條可追溯鏈即可回答 |
| E8 | 卡點處理成本 | 出錯後需要跨多少系統才能修？ | 優先局部修復，不擴散 |
| E9 | 可刪除性 | 新方案是否真的取代舊責任／狀態／步驟？ | 至少能指出實際刪除或合併項 |
| E10 | 實作增量 | 新增 schema／服務／規則的成本是否合理？ | 增量與可核對收益成比例 |
| E11 | 失敗模式 | 新方案失敗時是否會產生靜默錯誤／雙真值？ | 主要失敗可觀察且不製造雙真值 |
| E12 | 驗證方式 | 怎麼知道它比 baseline 改善？ | 有同一文本、同一專案、同一觀察指標的對照試跑 |

### 1.2 評價符號

- `P`：目前文件／邏輯足以支持通過。
- `R`：未解，需要定義或試跑。
- `F`：已發現直接衝突。
- `N/A`：該項對 baseline 或本候選不適用。

**不做總分。** 尚未定義權重前，把十二項相加沒有意義。

### 1.3 結論門檻

- **候選**：只有概念描述。
- **可試作**：沒有 E1／E2／E6／E11 的已知硬衝突，且 E12 可設計。
- **可比較**：已與 baseline 用同一案例跑完。
- **優於 baseline**：只能在事前指定指標上，對照資料真的改善後使用。

# Part A｜先處理舊版

## 2. B0｜現行 baseline：RBF1 + D48 + D37/D38 + D32～D34

### 2.1 評價假設

依本輪要求，**只在 D50 的比較場景中假設裁1～4都已啟用**；不改治理檔正式狀態。

為了讓假設可執行，暫採各案目前 Agent 建議：

- 裁1=A：WORK 卡住先最小診斷，再把人的能力缺口送 LEARN。
- 裁2=A：不把本趟「補過」自評升成跨趟真值。
- 裁3=A：usage 引用事件照記，成敗另記，不先造自動熟練度 Gate。
- 裁4=A：足以重試原呼叫節點即返回，成敗交回呼叫方。

這四項只用來建立 baseline，不視為使用者正式裁決。

### 2.2 現行流程投影

RBF1 的核心敘事：

```text
文本
→ AI 拆解／模塊化／抽邊／重組（L2）
→ 大／中／小流程＋策略卡點（L1）
→ 最小可行流程
→ 卡點才調 L2（L3）
→ 局部最小學習路徑
→ 返回原流程
```

D48 再把它包進：

```text
WORK
→ 人的能力缺口才呼叫 LEARN
→ LEARN 返回原呼叫節點
→ 需要正式結論才呼叫 VERIFY
```

D32～D34另外承接開發日誌／驗證項目／發布與對接。

### 2.3 B0 十二項自檢

| 指標 | 結果 | 理由 |
|---|---|---|
| E1 單一責任 | R | D48 把 WORK 設為外層，但 RBF1／D37仍以「文本→L1流程」描述主流程；Project／WORK 與 L1 流程的 owner 還沒有完全收斂 |
| E2 單一真值 | R | L2 擁有模塊／邊，L1擁有流程投影；兩者邏輯上可分，但「專案最小路徑」尚不是一個明確一級真值 |
| E3 必要步驟 | R | RBF1 主幹仍把 L2 備料排在流程之前；是否每次都必要尚未用專案案例證明 |
| E4 分支複雜度 | R | WORK→LEARN 路由、LEARN 內同層／降層、VERIFY 選配皆有合理用途，但未量測一次真實任務實際需多少路由判斷 |
| E5 重複處理 | R | 可能先全文備料，實際專案只用少數模塊；卡點又生成局部路徑，是否形成無效處理尚未量測 |
| E6 回寫衝突 | P | D38 已明定導航投影不回寫 L2；D34也要求內容／領域／治理詞彙分流 |
| E7 可追溯性 | R | 有來源、模塊、邊、使用／開發日誌，但缺少「一次 Project Run」把路徑、卡點、返回、結果串成單一紀錄 |
| E8 卡點處理成本 | P | RBF1 已有同層局部 LOOP，裁1/4 假設生效後入口／返回也清楚 |
| E9 可刪除性 | N/A | baseline 本身不是改版方案，不以刪除舊責任為要求 |
| E10 實作增量 | P | 主要能力已存在於現行分支；本項只把它當 baseline |
| E11 失敗模式 | R | 裁1=A 可降低工具／來源誤送 LEARN，但「文本主流程 vs Project/WORK」角色模糊仍可能造成錯層 |
| E12 驗證方式 | F | 新 D48＋裁1/4 尚未用同一個真實 Project 完成一次可對照重跑 |

### 2.4 舊版目前可確認的問題

在不評價任何新候選前，B0 已有四個必須先量測／釐清的問題：

1. **Project 是否是一級工作單位？**目前文件主要是一級「文本／來源／L1流程」，Project 多半是情境或 WORK 敘事。
2. **最小路徑的 owner 是誰？**目前有 L1 最小可行、L2 模塊／邊、L1-04 局部路徑，但「Project Minimum Path」沒有獨立真值定義。
3. **L2 是否被前置處理過量？**主幹先備料，專案實際使用比例未知。
4. **完整 Run Record 是否存在？**D32 有開發日誌，但尚未規定一次專案從起點→卡點→LEARN→返回→結果如何形成單一回合紀錄。

### 2.5 B0 結論

B0 **可作 baseline，但目前沒有資格稱為已優化**。

現有已知優點只有：

- L2 與導航回寫邊界已分開。
- 卡點可局部處理後返回。
- VERIFY 與任務驗收有詞彙／責任分流。

現有主要待驗證成本：

- 文本／學習敘事仍比 Project 敘事更上位。
- 模塊前置處理可能超過本次專案所需。
- 缺 Project Run 級完整紀錄。

**先處理 baseline 到此。以下才開始評價新候選。**

# Part B｜新候選逐版保留

## 3. B1｜Project-first 六步版

### 3.1 原始構想

```text
文本處理
→ Project／最小路徑
→ 卡點
→ 學習迴圈
→ 返回 Project
→ 本次完整紀錄
```

### 3.2 核心變更

- Project 取代「來源／L1學習流程」成為前台主體。
- Learn 只在卡點發生。
- 每次完成後必有 Run 級完整紀錄。

### 3.3 自檢

| 指標 | 結果 | 理由 |
|---|---|---|
| E1 | P | 主流程 owner 明確放在 Project |
| E2 | R | Module／Edge 與 Project Path 的關係未定義 |
| E3 | P | 表面必要步驟少；但文本處理內部做什麼尚未展開 |
| E4 | P | 主流程只有卡點時分支 |
| E5 | R | 模塊若仍照舊全文處理，重複問題仍存在 |
| E6 | R | Project Path 與 L2 誰能改誰未定義 |
| E7 | P | 明確要求完整 Run Record |
| E8 | P | Learn 是局部支線 |
| E9 | P | 可刪除「每份文本都必須先跑完整 L1學習」的敘事 |
| E10 | R | 需要正式定義 Project／Run／Minimum Path |
| E11 | R | 最大風險是模塊變死區，或之後再補一套模塊→Project 橋接 |
| E12 | R | 可以設同題試跑，但尚未執行 |

### 3.4 當前結論

**候選。** 最大未解不是 Project 本身，而是「模塊在這條流程裡到底做什麼」。

## 4. B2｜模塊雙用途／三出口版

### 4.1 原始構想

為避免 B1 讓 L2 變死區，將模塊設定為：

```text
文本
→ 模塊／邊庫
   ├─ Project 建立時：組最小路徑
   ├─ Project 卡點時：組局部學習路徑
```

| E3 | R | 若一定先模塊化才能出 Project Path，模塊變成前置 Gate |
| E4 | P | runtime 分支本身不多 |
| E5 | P/R | 模塊可同時供 Project 與 Learn reuse；但全量備料仍可能浪費 |
| E6 | R | L2 結構變更是否能自動改 Project 未定義 |
| E7 | P | Project Run 可記模塊引用 |

| E9 | R | 尚未證明能刪除 L1 路徑邏輯，可能只是多一個 Project 層 |
| E10 | R | 需要 Module↔Project Path 映射規則 |
| E11 | R | 主要風險是「模塊決定路線」和「Project 決定路線」角色重疊 |
| E12 | R | 可試，但要先定義 path owner |

### 4.3 當前結論

**候選。** 它解決模塊死區，但沒有解決「模塊是不是 Project 的前置條件／路線 owner」。

| E3 | P | 可以立即開跑，不需等待全量模塊化 |
| E4 | R | 增加「何時接受後台強化」的新分支 |
| E5 | F | 同一文本被 Project parser 與 L2 parser 各自結構化 |
| E6 | F | L2 完成後是否改動已執行中的 Project Path 會產生回寫衝突 |
| E7 | R | 若保留版本史可以追，但會增加 path version 管理 |
| E8 | P | 卡點仍可局部處理 |
| E9 | F | 沒有刪掉重複系統，反而並行兩套 |

| E11 | F | 靜默改路、雙真值是直接已知風險 |
| E12 | R | 可試，但概念硬衝突已足以阻止直接實作 |

### 5.3 當前結論

**不進試作。** 不是因為「不漂亮」，而是已命中 E1／E2／E5／E6／E11 的硬衝突。

保留本版是為了避免之後重新走回同一條路。

## 6. B4｜Project 唯一路線真值 + L2 純資源版

### 6.1 原始構想

```text
Project / WORK
→ 擁有 Goal、Minimum Path、Runtime State

L2
→ 只提供知識／方法／證據／能力資源
→ 可以提出 Route Suggestion
→ 不得直接修改 Project Path

LEARN
→ 卡點時查 L2，補完回 Project
```

### 6.2 自檢

| 指標 | 結果 | 理由 |
|---|---|---|
| E1 | P | Project 唯一擁有路線決策 |
| E2 | P/R | Project Path 唯一；但 Project Node 與 Module 是否重複表示同一能力仍未解 |
| E3 | R | 需要 Module→Project Node 的查找／映射 |
| E4 | R | Route Suggestion 接受／拒絕增加一個控制點 |
| E5 | R | Project Node 與 Module 可能保留兩份相近結構 |
| E6 | P | L2 不直接寫 Project，可避免自動回寫衝突 |
| E7 | P | Project Path + module refs + Run Events 可追 |
| E8 | P | 卡點留在原 Project Node，Learn 局部處理 |
| E9 | R | 可刪除 L2 對 Project 路線的寫入權，但仍保留兩套模型 |
| E10 | R | 需新增映射與 Suggestion 協議 |

## 7. B5｜Unified Graph：Module=Node，Project Path=子圖，Learn=Node 展開

### 7.1 原始構想

不再保留「Project Path 一套結構、Module/Edge 另一套結構」。底層只有一組圖資料：

```text
Node / Module
Edge
Path
Run
Event
```

語義：

```text
Project = Goal + Path + Runtime State
Path    = 為本次 Goal 從 Graph 選出的子圖／序列
Learning= 某個卡住 Node 的局部展開／補足
Record  = Run 的事件歷史
```

### 7.2 延伸策略 B5-a｜按需抽取

為避免「全文 80 模塊先建完才開工」：

```text
文本 + Project Goal
→ 只抽出完成 Goal 所需 Node／Edge
→ 同時形成第一版 Path
→ 立即執行
→ 其他內容延後；真的需要再增補
```

這是 B5 的抽取政策，不另立第二套 path generator。

### 7.3 自檢

| 指標 | 結果 | 理由 |
|---|---|---|
| E1 | P | Graph 結構只有一個 owner；Project／Learn 是同一資料的不同操作 |
| E2 | P/R | 理論上 Node/Edge 是單一結構真值；但「Run 臨時展開」是否回寫 Graph 尚未定義 |
| E3 | P/R | B5-a 可減少全量前置處理；但抽取 Goal 所需 Node 本身仍需最小處理 |
| E4 | P | 主路由可簡化為 Execute→Node 卡點→局部處理→重試 |
| E5 | P | 不需 Project Path parser 與 Module parser 各建一份流程結構 |
| E6 | F/R | 最大未解：卡點展開出的 Node 是 Run-local 還是可回寫通用 Graph；未定前存在污染風險 |
| E7 | P | Graph→Path→Run→Event 可以形成直接追溯鏈 |
| E8 | P | 卡點可直接附著在原 Node 局部展開 |
| E9 | P | 理論上可刪掉獨立 Project-node schema、獨立 Learn-path schema、Module↔Project mapping |
| E10 | R | 可能需要正式化 Path／Run／Event；現有 Module/Edge schema 能否直接承接尚未檢查 |
| E11 | F/R | 若 Run-local 學習結果錯誤回寫通用 Graph，可能污染後續所有 Project |
| E12 | R | 可設同題試跑，但要先解 E6/E11 |

### 7.4 當前結論

**候選，尚未達可試作門檻。**

原因不是概念本身，而是兩個硬問題未解：

1. **Node granularity**：知識模塊是否真的能直接等同 Project 執行節點？若不能，E2/E5 的「統一」是假統一。
2. **Run-local vs Graph write-back**：學習迴圈產出的細化節點／新邊什麼時候只屬本次 Run，什麼時候才有資格升成通用 Graph？

在這兩題未定之前，不得宣稱 B5 優於 B4 或 B0。

## 9. 「加項／減項／衝突項」比較

### B0 → B1

**加項**：Project、Minimum Path、Run Record。  
**減項**：把「每份文本的 L1學習流程」降為非預設主體。  
**衝突**：Module／Edge 的角色未定，可能死區。

### B1 → B2

**加項**：Module 作 Project 組裝庫＋Learn 補給庫＋沉澱來源。  
**減項**：避免 L2 只在卡點出現。  
**衝突**：Project Path 與 L2 Edge 都可能開始擁有路線語義。

### B2 → B3
