## 試跑結論（摘要）

1. **開發日誌 vs 驗證項目**：同一輪工作可並存——落檔三份 spec 是過程紀錄（開發日誌）；「分流表是否足夠」另建 L1 驗證項目，內容不重寫。
2. **詞彙對準**：【本次進展】已對準 agent-ops／模板；AGENTS 新增「共同語言」「詞彙分流」觸發詞，避免每次重對。
3. **L1 探路判斷**：**另開後續項目**——分流表可支撐 Agent 查表；第二道題（內容發布→F1 收錄）待另開 L1 或 L2。
4. **進圖**：本試跑未進 F2；若日後把驗證報告當來源，L2「建議採用」應標 `advice` 並保留適用範圍。

## 試跑後決策（ingest／V）

### ingest 標記

**現階段不提案** F1 硬欄位或 ModuleCore 新鍵。

理由：

- 試跑僅覆蓋「落檔＋詞彙對準」，未跑「發布內容→Inbox→模塊化」全鏈。
- `DocumentManifest` 備註層可自由文字標「內容驗證來源／驗證項目 ID」，不動 canonical。
- **觸發再提案**：第二題試跑完成 F1 收錄後，若反覆需手動解釋來源類型，再開輕量待裁。

### V 擴充檢查

**不升必做**；保留擴充心智模型一條（未寫入看板）：

> 已發布內容是否使用超出其驗證等級允許的判斷詞（如 L1 寫成「建議採用」）。

理由：

- 尚無對外發布實例；V1 現有五類驗證已覆蓋管線產物。
- **觸發再提案**：首篇對外驗證報告發布後，若需抽查，走 V 擴充檢查提案＋使用者確認。
